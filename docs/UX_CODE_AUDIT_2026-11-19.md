# Обзор UX и надёжности FitWeaver — 19.11.2026

Область: desktop GUI, конструктор, PlanStore, сборка FIT, архивирование и границы
фоновых операций. Прочитаны CLAUDE.md и TODO.md, выполнен `git pull --ff-only`.
Это обзор основных пользовательских сценариев, не построчная проверка всего репозитория.
Код приложения не изменён. Имеющиеся изменения eval_harness и его тестов сохранены.

Проверка: `python -m pytest tests/ -q` — 490 passed, 36 subtests passed; одно
предупреждение Starlette/httpx. Семь дополнительных offline probes прошли на временных
файлах; они подтверждают текущее ошибочное поведение, а не исправление. Локальный файл:
`Build_artifacts/audit_20261119/test_audit_repros.py` (не входит в Git).
GUI callbacks в probes вызываются с подставленными зависимостями; это не ручной
проход интерфейса. Garmin, часы, LLM и собранные exe в этом обзоре не проверялись.

## Ошибки по приоритету

### P1. Каденс теряется при открытии плана через PlanStore

`src/garmin_fit/plan_store.py`: `_SCHEMA`, `_insert_step`, `_get_steps`.
В WorkoutStep есть `cad_low`/`cad_high`, но в SQLite-схеме и сериализации их нет.
Они также не попадают в `extra`, поскольку являются известными полями домена.

Воспроизведение: открыть YAML с `dist_cadence`, `km: 1`, `cad_low: 170`,
`cad_high: 180`. Уже `store.get_plan()` возвращает границы None. Переименовать
любую тренировку — write-through перепишет весь YAML без границ каденса.
Исходный файл меняется только после операции записи, не при простом открытии.

Исправление: сохранять оба поля, учесть уже существующие workdb; проверить round-trip
каждого поддержанного типа шага через YAML → PlanStore → YAML → FIT/Garmin.

### P1. Старый черновик может перезаписать тренировку другого плана

`fitweaver_gui.py`: `_edit_selected_workout`, `_reload_yaml`, `_on_email_change`;
`gui_builder_tab.py`: `_builder_save_edit`.

Редактор запоминает только числовой `workout_id`. Открытие другого YAML заменяет
`self._store`, но не инвалидирует редактируемый черновик. В двух рабочих БД первая
тренировка обычно имеет ID 1. Открыть редактирование A, загрузить B, нажать «Сохранить
в YAML» — шаги и имя A записываются в B. Изолированный вызов callback это подтверждает.
Дополнительно при переключении на профиль без плана очищается календарь, но старый
`_store` остаётся доступен конструктору.

Исправление: привязать черновик к пути/профилю/ревизии плана; проверять их перед
сохранением. При смене контекста предложить сохранить черновик отдельно или закрыть
редактирование. Пустой контекст должен закрывать и обнулять store.

### P1. Неудачная сборка удаляет предыдущие FIT

`src/garmin_fit/orchestrator.py`: `run_generation_pipeline`, строки 109–112.
Очистка общего Output_fit происходит до подготовки и проверки YAML. На существующем
файле с содержимым `workouts: [` сборка завершается неуспешно, но предыдущий FIT уже удалён.
Подтверждено реальным pipeline с перенаправлением output/artifacts во временную папку.

Исправление: валидировать до любых изменений output; собирать в отдельную папку запуска
и публиковать результат после успешной проверки. При ошибке сохранять последний результат.

### P1. «Архивировать текущий план» архивирует все планы

`fitweaver_gui.py`: `_cmd_archive`; `workflow.py`: `workflow_archive`;
`archive_manager.py`: `_collect_plan_files`.
GUI обещает переместить текущий план, но передаёт только `archive --yes`. Без plan_paths
архиватор собирает все YAML/YML/MD из Plan/. План, выбранный вне Plan/, вообще не включается
этим способом. Это несоответствие подтверждения реальному объёму операции.

Исправление: передавать выбранный путь и связанные с ним артефакты. Для отдельной операции
«Архивировать всё» показывать конкретный список файлов. Подтверждены аргументы callback
и ветка выбора файлов; пользовательские файлы не перемещались.

### P2. Ошибка записи YAML не откатывает изменения SQLite

`plan_store.py`: например, `rename_workout_filename`, `replace_workout_steps`.
Сначала выполняется commit БД, затем `_write_through`. При OSError YAML остаётся прежним,
а рабочая БД уже изменена. Следующая удачная операция записывает также правку, которую
приложение ранее считало неуспешной. Воспроизведено подстановкой ошибки диска.

Исправление: единый протокол сохранения с восстановлением рабочей копии при ошибке;
YAML остаётся источником истины. Атомарная замена файла сама по себе не делает SQLite
и YAML общей транзакцией. Дополнительно проверять внешние изменения YAML по hash/ревизии.

### P2. Успешная проверка одного файла помечает готовым другой

`fitweaver_gui.py`: `_handle_cli_result`.
Callback `validate-yaml --plan A` выставляет общий `_yaml_ready=True`, не проверяя,
что текущий путь всё ещё A. Поля/combobox профиля не блокируются `_begin_operation`,
который обходит только Button. Проверено вызовом callback при выбранном B.
Это неверный статус готовности; сборщик дополнительно валидирует файл самостоятельно.

Исправление: передавать в результат operation_id, путь, hash входа и профиль;
устаревший результат показывать в истории, не применять к текущему плану.

### P2. Добавление тренировки допускает дубли имени в YAML

`gui_builder_tab.py`: `_builder_commit`; `plan_store.py`: `add_workout`.
Проверяется отдельный черновик, но не его уникальность внутри текущего плана.
Добавление тренировки с уже существующим filename записывает YAML, который затем
не проходит валидацию. Аналогичная проверка есть в replace_workout_steps, но не в add_workout.
Воспроизведено добавлением имени, прочитанного из загруженного store.

Исправление: проверять весь результирующий план до записи; предложить новое имя или
осознанную замену. Перенос календарём тоже должен проверять коллизии имён.

## Предложения по UX/UI

1. **Первый экран — действия пользователя.** «Вставить план», «Создать тренировку»,
   «Открыть план». Затем единый маршрут: ввод → проверка → календарь → отправка.
   Простой/экспертный режим уже есть; развить его, не создавать ещё один переключатель.
2. **В простом режиме показывать тренировку, а не YAML.** Карточки шагов, раскрываемые
   повторы, дистанция и известная длительность. YAML оставить доступным в экспертном режиме.
   Кнопку «Генерировать YAML» назвать «Разобрать план»; рядом объяснять, нужен ли LLM.
3. **Сохранять черновики.** Сейчас текст, результат генерации и шаги конструктора не входят
   в `_save_session`; `_on_close` не предупреждает о них. Добавить автосохранение черновика
   по профилю, восстановление после запуска и Undo/Redo для конструктора/календаря.
4. **Показывать исправления рядом с тренировкой.** Например: «Пульс до 140 → 60–140»;
   «Не указана длительность → завершение кнопкой Lap». При частичном разборе дать список
   нераспознанных тренировок и повтор только для них. Сейчас подробности уходят в лог.
5. **Предпросмотр отправки.** Таблица: дата, тренировка, создать/пропустить/заменить,
   причина, выбранный профиль. Подтверждение должно отражать реальные изменения после
   фильтрации, а результат — отдельный статус каждой тренировки и возможность повторить ошибки.
6. **Удобнее редактировать повторы и даты.** Показывать повтор как вложенную группу;
   перемещать группу целиком. Сейчас наличие любого repeat блокирует перестановку шагов.
   Дату выбирать отдельно от технического filename, поля интенсивности подписать по-русски.
7. **Различать состояния.** «Черновик», «Сохранено локально», «FIT собран», «Назначено в
   Garmin» — разные результаты. Не сводить частичную готовность и промежуточный `[OK]`
   к общему зелёному «Готово». Цвет дополнять текстом/значком.

## Внутренняя логика и порядок работ

- Сначала исправить P1 и добавить регрессии на потерю данных и смену контекста.
- Ввести общий сервис операций плана: validate → применить изменение → сохранить →
  сообщить результат. GUI не должен сам согласовывать SQLite, файл и выбранный профиль.
- Хранить дату тренировки явно в доменной модели; filename выводить из неё. Переход сделать
  совместимым со старыми YAML. Это уберёт часть неоднозначности года и переименований.
- Фоновые задачи получают неизменяемый снимок параметров; GUI применяет только актуальные
  результаты. Mixin-разделение файлов уже сделано частично, но общее изменяемое состояние осталось.
- После надёжного сохранения внедрить автосохранение, Undo/Redo и предпросмотр отправки.
- Затем упрощать первый экран и представление тренировок. Полная смена GUI-фреймворка
  не требуется для перечисленных улучшений.
- Продолжить live LLM/часовые проверки из TODO отдельно. Чистые unit-тесты не подтверждают
  качество модели, работу реального аккаунта или поведение диапазона пульса на часах.
